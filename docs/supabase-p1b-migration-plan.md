# Supabase shared business data P1B migration package

Status: release-candidate package after executable validation on a disposable local Supabase stack. No SQL in this package has been applied to production.

## Scope

P1B creates only:

- `public.business_users`
- `public.brands`
- `public.platforms`
- `public.campaigns`
- private authorization/timestamp helpers required by those tables
- strict production bootstrap data for the six existing business users
- stable platform compatibility records `p1..p4`

It does not create or migrate shifts, shift registrations, reports, dashboard updates, swaps, attendance, analytics, or files. It does not change `dataService.ts` or any runtime persistence selection.

The mock brands `b1..b4` and campaigns `c1..c3` are development/test fixtures, not production bootstrap. Their DiceBear images, `.example`/`example.com` URLs, generic names, and runtime-relative `c3` dates establish that classification.

The first two migrations are schema-only and replay without application Auth rows. The third is deliberately strict production bootstrap and must fail if its six Auth prerequisites are absent or inconsistent. Test fixtures are outside `supabase/migrations`, require an explicit `app.p1b_fixture_mode=isolated-test` session setting, and cannot be included by `supabase db push` migration discovery.

## Table definitions

### `business_users`

Uses the current domain `User` shape and text business IDs. `auth_user_id uuid` is a nullable, unique foreign key to `auth.users(id)` with `ON DELETE SET NULL`. Business relations continue to use `business_users.id`.

It includes display/contact fields, legacy `role`, authoritative `system_permission`, `operational_roles text[]`, department, business/account status, email-verification display metadata, provider, join date, timestamps, and current lifecycle metadata. It contains no Auth credentials or session material.

### `brands`

Preserves all current Brand knowledge fields, contact fields, content-guidance arrays, status, actor references, timestamps, and lifecycle metadata.

### `platforms`

Preserves all current Platform fields. `account_information` is operational description only and must not contain credentials. The stable platform catalog `p1..p4` is production compatibility reference data because these IDs are used by templates and future Shift migration. The migration stores no platform secret.

### `campaigns`

Preserves Brand ownership, date range, URLs/preview fields, platform compatibility array, status, owner, timestamps, and lifecycle metadata. `brand_id` is a restrictive FK. `platform_ids` remains `text[]` for P1 compatibility. Demo campaign fixtures validate their referenced platform IDs.

## Identity and authorization

The database relation is authoritative:

```text
auth.uid()
  -> business_users.auth_user_id
  -> active business user
  -> business_users.system_permission
```

JWT `app_metadata` remains the existing application bootstrap mapping, but RLS does not authorize from JWT metadata. It never reads `user_metadata`, request roles, or arbitrary headers.

Private helper functions:

- `private.current_business_user_id()`
- `private.current_business_user_is_active()`
- `private.current_system_permission()`
- `private.is_admin()`
- `private.is_leader_or_admin()`

The lookup helpers are `STABLE SECURITY DEFINER`, have `search_path = ''`, use fully qualified tables, derive identity from `auth.uid()`, live outside the exposed schema, and have explicit execute grants only for `authenticated`. The updated-at trigger is `SECURITY INVOKER`.

## RLS matrix

| Table | Member | Leader | Admin |
|---|---|---|---|
| `business_users` | Read active directory rows | Read active directory rows | Full management and historical visibility |
| `brands` | Read active/non-deleted rows | Read active/non-deleted rows | Full CRUD |
| `platforms` | Read active/non-deleted rows | Read active/non-deleted rows | Full CRUD |
| `campaigns` | Read active/non-deleted rows | Read active/non-deleted rows | Full CRUD |

All access requires an active, mapped business user. `anon` receives no table access. Leader campaign operational editing intentionally remains denied in P1B because the current permission requires a field whitelist; it must be implemented later through a controlled mutation rather than a broad table UPDATE policy. Member self-profile editing is also deferred to a whitelist mutation.

Email and phone both remain readable team-wide to active authenticated business users in P1B. Table RLS does not provide column-level privacy. This is an explicit MVP decision, not a claim that phone is field-restricted. If phone visibility is later rejected, introduce a security-invoker safe-directory view or server endpoint before runtime cutover rather than weakening base-table policies.

## Constraints and indexes

- Text primary keys preserve the current IDs.
- `business_users.auth_user_id` and case-normalized email are unique.
- Permission, role, status, account status, provider, knowledge status, and campaign status have checks.
- Operational roles are limited to `host`, `support`, and `technical`.
- Campaign end date cannot precede start date.
- Actor references use `ON DELETE SET NULL`; the campaign-to-brand FK uses `ON DELETE RESTRICT`.
- FK, active-row, campaign date/status, and array lookup indexes cover the current P1B access patterns.

## Timestamp behavior

All authoritative audit/lifecycle timestamps use `timestamptz`. Inserts default to server time. The trigger always assigns `updated_at = statement_timestamp()` on UPDATE. Baseline inserts explicitly preserve historical `created_at` and `updated_at`; idempotent reruns do not update equal or newer rows.

## Six-user mapping

The production bootstrap resolves each account by normalized email from `auth.users` and requires exactly one result:

| Business ID | Email | Permission |
|---|---|---|
| `1` | `admin@livestream.com` | `admin` |
| `2` | `leader@livestream.com` | `leader` |
| `3` | `host1@livestream.com` | `member` |
| `4` | `host2@livestream.com` | `member` |
| `5` | `support1@livestream.com` | `member` |
| `6` | `technical1@livestream.com` | `member` |

It verifies the existing `raw_app_meta_data.business_user_id` and `system_permission` values before inserting. Missing, duplicate, or mismatched Auth users abort the transaction. Production bootstrap never creates Auth users and never changes Auth metadata, email, or credentials.

## Bootstrap and fixture classification

- **Production bootstrap:** business users `1..6` and stable platform catalog `p1..p4`.
- **Development/test fixtures:** brands `b1..b4` and campaigns `c1..c3`.
- **`c3` classification:** demo fixture. Its source is `format(new Date())` through `addDays(new Date(), 7)`, so `2026-08-11` through `2026-08-18` is only a deterministic test snapshot and never production data.

Bootstrap and demo fixtures use `INSERT ... ON CONFLICT (id) DO UPDATE` with a guard that updates only when the existing row's `updated_at` is older than the baseline. `created_at` is never rewritten. Equal/newer rows are preserved, and critical Auth mapping is verified after the production upsert.

`p1b_auth_users.sql` creates deterministic UUID placeholders in isolated databases only. It contains no sign-in secret and is never part of production migration order. It supplies the exact app metadata required to test both successful bootstrap and failure cases without weakening production preconditions.

## Clean replay strategy

1. Replay schema through `20260811110239` with no seed.
2. In one explicit isolated-test database session, set `app.p1b_fixture_mode=isolated-test` and load `p1b_auth_users.sql`.
3. Apply the pending `20260811112834` production bootstrap migration locally.
4. Optionally load `p1b_demo_master_data.sql` under the same fixture guard.
5. Re-run bootstrap/fixture assertions to prove idempotency and failure behavior.

This keeps schema migrations independently replayable while preserving a strict production bootstrap. A normal production `db push` never discovers files under `supabase/tests/fixtures`.

## Executable validation completed

P1B-X replayed the three migrations on a disposable local Supabase CLI stack and verified:

- migration history contains exactly the three production migrations in order;
- the guarded Auth fixture maps all six expected users and the production bootstrap reruns idempotently;
- missing user, duplicate normalized email, wrong `business_user_id`, and wrong `system_permission` all fail closed;
- demo fixtures remain outside migration history and load four brands plus three campaigns;
- anon, Member, Leader, Admin, unmapped, inactive, archived/deleted, and forged-claim personas match the RLS matrix;
- Member/Leader writes and sensitive user mutations are denied, while Admin CRUD succeeds;
- private `SECURITY DEFINER` helpers retain hardened search paths and restricted grants;
- database lint reports no errors and the security advisor reports no warnings;
- static migration contracts, TypeScript, and the production application build pass.

The reusable executable checks now live under `supabase/tests/`. They require the explicit session guard `app.p1b_fixture_mode=isolated-test`, use transactions for destructive cases, and remain outside production migration discovery.

The production project was independently verified as having zero P1B business tables, empty remote migration history, and the expected six Auth metadata mappings. No remote DDL, migration-history repair, Auth mutation, link operation, or database push was performed by P1B-R.

## Advisor review

The performance advisor reports four `multiple_permissive_policies` warnings for `SELECT`:

| Table | Shared policy | Admin policy | Assessment |
|---|---|---|---|
| `business_users` | `business_users_active_directory_select` | `business_users_admin_all` | Intentional: active users see the active directory; Admin also needs archived/deleted history. |
| `brands` | `brands_shared_select` | `brands_admin_all` | Intentional: team-wide active-row reads overlap Admin full-history access. |
| `platforms` | `platforms_shared_select` | `platforms_admin_all` | Intentional: team-wide active-row reads overlap Admin full-history access. |
| `campaigns` | `campaigns_shared_select` | `campaigns_admin_all` | Intentional: team-wide active-row reads overlap Admin full-history access. |

PostgreSQL ORs permissive policies. For Admin SELECTs, both the shared active-row predicate and `private.is_admin()` can be evaluated. The helpers are stable, their calls are wrapped as scalar subqueries for init-plan evaluation, and P1B exposes only four small master tables, so the expected initial overhead is low. Consolidation is technically possible by folding Admin visibility into one SELECT policy and splitting Admin INSERT/UPDATE/DELETE into command-specific policies, but that increases policy count and changes a security-sensitive contract. The current overlap is explicit and tested, so P1B-R does not rewrite production policies merely to silence the advisor. Reassess from production query telemetry before P1C or when table volume grows.

The 16 `unused_index` infos cover operational-role and campaign platform GIN indexes, lifecycle/actor foreign-key indexes, active-name indexes, the business-user active lookup, and campaign owner/status/date access paths. The database is newly replayed and has no representative workload, so `pg_stat` cannot establish that these indexes are unnecessary. No index is structurally duplicated; each has a distinct key, predicate, or access method. P1B-R retains all 16 and defers usage review until representative production telemetry exists.

Email and phone visibility remains an explicit MVP product decision: every active authenticated business user may read both fields for the active team directory. This is base-table RLS, not column-level RLS. P1B-R does not introduce a privacy view or RPC; any future restriction must be designed before runtime persistence cutover.

## Legacy `schema.sql`

`supabase/schema.sql` is an obsolete draft, not authoritative migration history. Git shows it was first added, removed during the pnpm workspace scaffold, and re-added in commit `0504436`; there are no historic `supabase/migrations` files proving it was applied. It conflicts with P1B through UUID domain IDs, `public.users`, incomplete fields, broader RLS, and a public unhardened Auth trigger.

The reported production public schema is empty, which supports the file being unapplied there, but remote migration history has not been verified from this workstation. P1B can become the authoritative baseline only after read-only remote history confirms there is no conflicting applied migration.

## Rollback

Before production APPLY, take a schema/data backup and retain the prior application deployment. Because P1B does not switch runtime reads or writes, applying the schema alone does not change current application behavior. If staging validation fails, discard the disposable staging database and correct the migration through a new reviewed migration.

After a production migration has been applied, do not rewrite migration history or run a destructive down migration. Roll forward with a corrective migration. Runtime cutover will be a separate checkpoint and must fail visibly on database errors; production must never fall back silently to mock data.
